# Стройконтроль ПТО — Compose namespace

Пространство для ПТО и сметного отдела строительной организации (ТЗ из `Документ2.docx` и требования MVP):

1. **Документы объекта** — комплекты ПД и РД по версиям, комплектность по ведомости томов, какая версия с какой сравнивается.
2. **Сравнение ПД и РД** — сверка PDF проектной и рабочей документации, итерации «до/после».
3. **Замечания экспертизы** — реестр по выгрузкам Excel, история итераций, проверка ответов по документам.
4. **Проверка исполнительной документации** (АОСР/АООК ↔ реестр ↔ КС-2; раньше — отдельное пространство `stroykontrol-id`, теперь здесь).
5. **Проверка формирования ВОИСР** — сверка объёмов/стоимости ВОИСР со сметной документацией.

## Навигация («от объекта»)

Боковое меню — группы и списки (описание в `pages.mjs`):

| Раздел | Что внутри |
|---|---|
| **Главная** | «Требует внимания» (метрики) и список объектов |
| **Объекты** | список; карточка объекта — рабочее место с вкладками **Обзор** (документы, комплектность, «ПД v2 ↔ РД v1»), **Комплекты**, **Ведомость томов**, **ПД ↔ РД**, **Замечания экспертизы**, **Исполнительная документация**, **Сметы и ВОИСР** |
| **Проверки** | сквозные списки: комплекты, сравнения, расхождения, замечания, пакеты ИД, замечания по ИД, проверка ВОИСР |
| **Справочники** | ведомость состава томов, нормативные документы, юрлица, специалисты НРС |
| **Служебное** | документы сравнений, журналы, акты и строки реестров, сметы, демо-объекты |

Карточки записей скрыты из меню и открываются из списков. **Демо-данные** (объекты `OBJ-000N` из `seed.mjs` и всё к ним относящееся) помечены `data_kind = demo` и скрыты из рабочих списков и метрик (фильтр `REAL` в `pages.mjs`); их список — «Служебное → Демо-данные». Пометка: `mark_demo.sql` (пробный прогон по умолчанию, `-v apply=1` — применить). Записи без `data_kind` считаются рабочими.

### Комплекты документов

`document_sets` (объект, стадия ПД/РД, версия, дата, статус) — файлы (`cmp_documents.set`) загружаются в комплект один раз и используются любым числом сравнений. Сравнение указывает `set_pd` и `set_rd`; агент пишет подпись `sets_label` («ПД v2 ↔ РД v1»), а кнопка «Проверить комплектность» (rule chain `stroykontrol-check-sets`, `POST /api/sets/check`) читает ещё не прочитанные файлы, сверяет тома с ведомостью `object_volumes` и записывает `volumes_present/total`, `completeness_pct`, `completeness_note`. «Не последняя версия» агент заявляет только если есть комплект той же стадии с более поздней датой выпуска или этот комплект помечен «Заменён новой версией»; комплекты без дат — просто части (например, разные тома).

Разовые миграции (пробный прогон по умолчанию): `migrate_id_into_main.sql` — перенос пространства `stroykontrol-id` в `stroykontrol` (меняется только `rel_namespace`, ID не меняются; переводы переписываются; перед запуском — дамп в `backup/`, он в git не попадает); `migrate_sets.mjs [--apply]` — собирает комплекты из документов существующих сравнений (одинаковые «объект + сторона + метка `doc_version`» — один комплект). После миграции перезапустите сервер Compose (кэш).

Паттерн тот же, что у `agents/invest/compose`: `apply.mjs` идемпотентно создаёт namespace / модули / страницы по REST API Compose (обновляет по `handle`, id сохраняются).

## Apply

Сервер должен быть поднят на БД `test11` (сейчас — `bin/test11 serve-api`, слушает `:3333`, API-only без встроенного webapp).

```bash
cd agents/stroykontrol/compose
COMPOSE_DSN='postgres://postgres:Zse45rdx@127.0.0.1:5432/test11?sslmode=disable' \
  node apply.mjs
```

| Variable | Default |
|---|---|
| `COMPOSE_API` | auto-detect `http://localhost:3333/api/compose` → `/compose` |
| `TOKEN` | обмен refresh-токена из Postgres (см. `helpers.mjs: mintToken`) |
| `COMPOSE_DSN` | нужен для минта токена и как первый кандидат; по умолчанию перебирает test10/test9/test3 |

Пример замечаний к реальным документам ИССО 3.10 (три замечания и ответы из «Ответов на замечания №10351-РП») — `compose/examples/expertise-10351-RP.xlsx` (`go run fixtures/gen_remarks.go`), загружается в объект «ИССО 3.10». Выгрузку замечаний экспертизы к объекту прикладывает и импортирует `node load_expertise.mjs "<файл.xlsx>" --code <код объекта>`.

Пишет `applied.json` с ID (namespace/модули/страницы).

Сервер `test11` не отдаёт webapp (только API) — чтобы открыть пространство визуально в Compose Studio/Builder, нужно указать webapp (dev-сервер vite или собранный бандл) на `COMPOSE_API=http://localhost:3333`.

## Модель

| Модуль (`handle`) | Роль |
|---|---|
| **Объекты** (`objects`) | НСИ: строительный объект — общий контекст для всех трёх задач |
| **Сравнения ПД/РД** (`pd_rd_comparisons`) | Задание на сравнение: `pd_file`/`rd_file` (один файл на стадию) и/или комплект в `cmp_documents`, статус, % схожести, отчёт |
| **Комплекты документов** (`document_sets`) | Комплект ПД или РД объекта одной версии: стадия, версия, дата, статус, комплектность (считает агент) |
| **Ведомость состава томов** (`object_volumes`) | Ожидаемые тома объекта (шифр, наименование, стадия, обязательность) — эталон комплектности |
| **Сравнения ПД/РД** — поля сверх базовых | `kind` (ПД → РД / версии «до → после»), `pairing` (ручное сопоставление, JSON), `pairs_json` (результат сопоставления), `set_pd`/`set_rd`, `sets_label` |
| **Документы сравнения** (`cmp_documents`) | Файл комплекта (`set`) или файл, приложенный прямо к сравнению (`comparison`): стадия (`ref` = ПД-эталон / `target` = РД), файл, шифр и наименование тома (определяет агент по основной надписи; `detected_by = manual` — правка вручную не перезаписывается), число страниц |
| **Расхождения ПД/РД** (`pd_rd_discrepancies`) | Расхождения: вид, критичность, страница и область (`bbox_*`) в ПД и в РД, фрагмент, обоснование (`evidence`), решение проверяющего (`status`), `fingerprint` для переноса решений между запусками |
| **Замечания экспертизы** (`expertise_remarks`) | Реестр замечаний объекта по выгрузкам Excel: текст, ссылки на тома, ответ и предыдущий ответ, причина отклонения, НД, эксперт, критичность, итерации, **рабочий статус** (правится вручную; выгрузка меняет его, только если решение изменилось в экспертизе), исполнитель, срок, результат проверки по документам |
| **История замечаний** (`expertise_remark_history`) | Состояния замечания по итерациям и смены статуса (из выгрузок и вручную) |
| **Происхождение замечания** (`origin`) | `expertise` — из выгрузки экспертизы; `comparison` — сформировано агентом по подтверждённым находкам сравнения (`source_comparison`, `group_key` — ключ листа; номера `ПТО-<партия>.<n>`) |
| **Разбор ИИ** (`expertise_remarks.ai_verdict/ai_note/ai_at`) | Подсказка модели по фрагментам связанных томов; рабочий статус не меняет |
| **Журнал выгрузок замечаний** (`expertise_imports`) | Что изменила каждая выгрузка: новые, изменённые, смены статуса, возвращённые, исчезнувшие |
| **Карточки замечаний** (`remark_cards`) | Карточка из выбранных расхождений: документы, листы, в чём расхождение, что требуется, черновик ИИ (по кнопке), итоговый текст, статус |
| **Реестр ИД** (`id_registry`) | Эталонный список требуемых документов ИД по объекту |
| **Файлы ИД** (`id_files`) | Загруженные файлы + распознанные реквизиты + статус сопоставления с реестром |
| **Проверки комплектности ИД** (`id_check_runs`) | Итог прогона: всего/загружено/отсутствует/несоответствий |
| **Позиции смет** (`smeta_items`) | Импортированные строки сметной документации |
| **Позиции ВОИСР** (`voisr_items`) | Позиции ВОИСР подрядчика, привязка к смете |
| **Результаты проверки ВОИСР** (`voisr_check_results`) | Сравнение объём/сумма по ВОИСР vs смета, статус |

Модули ИД (`packages`, `acts`, `registry_rows`, `findings`, `participants`, `organizations`, `nrs_specialists`, `norm_docs`, `position_summary`) определены в `modules_id.mjs`; пакет ИД ссылается на объект (`object_ref`). Страницы: см. «Навигация».

## Тестовые данные

```bash
cd agents/stroykontrol/compose
COMPOSE_DSN='postgres://postgres:Zse45rdx@127.0.0.1:5432/test11?sslmode=disable' \
  node seed.mjs
```

Генерирует ≥100 (по умолчанию 120, `SEED_OBJECTS=`) объектов строительства, и на каждый — полный комплект документов: реестр ИД, загруженные файлы ИД (с реальными вложенными `.docx` и статусом сопоставления с реестром), сравнение ПД/РД (тоже с вложенными файлами ПД и РД + расхождения по страницам), позиции сметы и ВОИСР со сверкой объёмов/сумм. Идемпотентно — при повторном запуске, если объектов уже достаточно, ничего не досоздаёт (`SEED_FORCE=1` — досеять поверх). `filegen.mjs` — генератор минимальных `.docx`-вложений и загрузка через `/record/attachment` (тот же приём, что в `agents/invest/compose/seed_files.mjs`).

Итог одного прогона (120 объектов, ~9 сек): 3587 записей — `id_registry` 752, `id_files` 754, `pd_rd_comparisons` 155 (+282 расхождения), `smeta_items` 680, `voisr_items` 362 (+362 результата проверки), `id_check_runs` 120.

## Не реализовано в этом apply (нужна отдельная проработка)

Сам apply создаёт только структуру данных (namespace/модули/поля/страницы). Ничего из следующего не реализовано:

- OCR сканов в сравнении ПД/РД (сравнение комплектов PDF по тексту, таблицам, ключевым параметрам и чертежам делает агент `stroykontrol`, пакет `cmp/`, см. README агента). Цепочка `stroykontrol-compare-pd-rd` лишь запускает его (`STROYKONTROL_AGENT_URL`, по умолчанию `http://localhost:8092`).
- Импорт реестра ИД (XLSX/CSV/XML) и распознавание файлов ИД — п. 4.1.1–4.1.3 ТЗ №2.
- Парсинг смет (XLSX, Гранд-Смета `.gsf/.gsp`, АРПС) и автосопоставление с ВОИСР — п. 4.1.1–4.1.4 ТЗ №3.
- Формирование отчётов в PDF/DOCX/XLSX.

Это отдельные бэкенд-сервисы (по аналогии с `agents/invest` → `invest-engine`/`calc-evm`) или rule chains с HTTP-узлами; данные для их результатов поля модулей уже держат.
