# Шина сообщений

Функция шины сообщений позволяет инстансу-**производителю** перекладывать часть работы на инстанс-**потребитель** через очереди сообщений.
Шина сообщений в первую очередь предназначена для использования с рабочими процессами, но её можно расширить для работы в других местах.

!!! caution
    *DevNote*: следующее содержимое находится в стадии разработки и требует гораздо больше работы с низкоуровневой точки зрения.


## Терминология

[cols="1s,5a"]
|===
| [#messagebus-terminology-queue]#[messagebus-terminology-queue,Очередь](#messagebus-terminology-queue,Очередь)#
|
Очередь сообщений — это комбинация **названия**, **потребителя** и **метаданных**.
Метаданные используются для предоставления контекстной информации производителю и потребителю.

| [#messagebus-terminology-queue*producer]#[messagebus-terminology-queue*producer,Производитель очереди](#messagebus-terminology-queue_producer,Производитель очереди)#
|
Производители помещают сообщения в очередь сообщений.
Из коробки шина сообщений определяет производителей как обработчики рабочих процессов, к которым можно получить доступ через функцию **Отправка сообщения в очередь**.

| [#messagebus-terminology-queue*consumer]#[messagebus-terminology-queue*consumer,Потребитель очереди](#messagebus-terminology-queue_consumer,Потребитель очереди)#
|
Потребители — это адаптеры, которые потребляют сообщения из очереди сообщений.
Каждый потребитель реализован для конкретного назначения сообщения.
Из коробки шина сообщений определяет потребителей для шины событий и хранилища.
|===

## Жизненный цикл сообщения очереди

### Запись в потребителя

.Пример рабочего процесса:
- зарегистрируйте обработчик очереди
- используйте глобальный сервис шины сообщений и `push()` полезную нагрузку в конкретную очередь
- полезная нагрузка помещается во внутренний канал шины сообщений
- вызывается конкретный потребитель (хранилище), указанный для этой очереди
- адаптер-потребитель помещает полезную нагрузку в назначение
** это может быть другая очередь в хранилище
** это может быть шина событий, которая запускает другой рабочий процесс

### Чтение из производителя

Производители специфичны для реализации; LowCoooode использует конкретного как обработчик очереди рабочего процесса, где полезная нагрузка записывается в очередь через механизм шины сообщений.

Метаданные задержки опроса — это единственные метаданные, используемые в производителе хранилища для опроса данных БД, пока не будет реализован подписчик.
Таким образом, мы можем получать контекстные данные производителю/потребителю.

### Внутренний поток шины сообщений LowCoooode в шину событий

LowCoooode Workflow в настоящее время имеет возможность включения возможностей шины сообщений через механизм шины событий.
Производитель шины сообщений может в этом случае быть обработчиком шины событий, в нашем случае уже реализованным триггером очереди (см. [документацию по рабочим процессам/автоматизации](modules/integrator-guide/pages/automation/workflows/index.md)).

Обработчик очереди (производитель на диаграмме) должен быть запущен для записи в очередь шины сообщений; это делается через механизм шины событий.
Как только полезная нагрузка достигает производителя, полезная нагрузка и название очереди помещаются во внутренний канал сервиса шины сообщений (через открытый метод).

!!! caution
    Полезная нагрузка не проверяется, она обрабатывается как тип `[]byte`, и любая маршализация или декодирование должны выполняться на стороне потребителя.


Как только сервис шины сообщений получает соответствующую полезную нагрузку из внутреннего канала, он сопоставляет её с уже зарегистрированным и инстанцированным обработчиком-потребителем для этой очереди.
Затем полезная нагрузка обрабатывается в логике, специфичной для потребителя.

Поток сообщений в нашем примере ещё не завершён, так как у нас также есть потребитель шины событий, поэтому полезная нагрузка снова преобразуется (в рабочем процессе), и другая полезная нагрузка затем помещается в какую-то другую очередь.

Примером может служить страница регистрации на сайте, которая помещает идентификатор пользователя GitHub в очередь (назовём её `users_github`).
Шина событий затем получит полезную нагрузку с идентификатором, получит метаданные пользователя из GitHub, запишет их в хранилище и при успехе запишет через шину событий в другую очередь с URL аватара пользователя (назовём её `users_avatars`).
Шина событий запустит новый рабочий процесс в этой очереди, который получит бинарные данные по URL и запишет их в указанное хранилище.

### Очереди шины сообщений как распределённый конвейер

Продолжая наш предыдущий пример: когда наш сайт вырастет и мы масштабируемся на наших инстансах, мы также сможем переложить (если захотим) любую работу с рабочих процессов на выделенный сервис или нашу расширенную инфраструктуру у поставщика услуг.

Аналогично предыдущему сценарию, при регистрации пользователя потребитель шины сообщений должен знать, как помещать полезные нагрузки в механизм очередей поставщика услуг (например, Amazon SQS / SNS).
Затем инфраструктура, которую мы настроили, обработает все полезные нагрузки и использует нашего конкретного производителя шины сообщений (например, lambda-обработчик, написанный на Python), чтобы отправить полезную нагрузку на другой инстанс LowCoooode через механизм API-приёмника.

Рабочие процессы LowCoooode также включают триггер для [API-приёмника](devops-guide/sink-route), поэтому полезная нагрузка затем будет обработана в другом рабочем процессе в соответствии с бизнес-логикой всего потока.

Диаграмма, показывающая возможности создания конвейеров между различными механизмами очередей

[plantuml,msg-flow-1,svg,role=msg-flow-1]
@startuml
node "Domain" {
package "LowCoooode 1" {
  [Queue "users"]
}

package "LowCoooode 2" {
  [Queue "administrators"]
}

}

package "LowCoooode 3" {
  [LowCoooode API sink]
  [Queue "processed user data"]
}

cloud "Cloud service provider" {
  [Queueing mechanism]
  [Worker]
}

database "Store" {
    [Enriched user data]
}

[Queue "users"] --> [Queueing mechanism]
[Queue "administrators"] --> [Queueing mechanism]
[Queueing mechanism] --> [Worker]
[Worker] --> [LowCoooode API sink]
[LowCoooode API sink] --> [Queue "processed user data"]
[Queue "processed user data"] --> [Enriched user data]
@enduml
