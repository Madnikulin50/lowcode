# Workflow

Рабочий процесс LowCoooode (далее именуемый рабочим процессом) позволяет реализовать пользовательскую бизнес-логику без необходимости каких-либо знаний программирования.

!!! note
    *DevNote* предоставить некоторые диаграммы, касающиеся пакетов и потоков.


## Структура пакетов

Основная логика рабочих процессов реализована в пакетах `automation` и `wfexec`.
Кроме того, каждый основной сервис предоставляет свой собственный суб-пакет `automation`, который определяет определения типов и определения функций-обработчиков.

Пакет `automation` отвечает за операции CRUD над ресурсами, которые определяют автоматизацию, такими как рабочий процесс и триггер.
Кроме того, он отвечает за настройку и управление механизмом, который готовит, выполняет и возобновляет рабочие процессы.

Пакет `wfexec` отвечает за выполнение предоставленной автоматизации в предоставленном контексте.
Пакет `wfexec` не знает о родительском пакете automation и может выполнять любой допустимый набор интерфейсов `wfexec.Step`, представленных в виде графа.

### `/automation`

.Ключевые моменты пакета `automation`:
- **Рабочий процесс** инкапсулирует логику и метаданные автоматизации.
Рабочий процесс не обязательно действителен или исполняем.
- **Триггер** инкапсулирует логику и метаданные, определяющие, когда рабочий процесс должен выполняться.
- **Сессия** инкапсулирует рабочий процесс, который ещё не завершён (например, запущен, приостановлен или завершён).
Сессия может быть сброшена в базу данных и перезапущена в более поздний момент времени.
- **Реестр автоматизации** содержит определения типов и обработчиков, которые может использовать автоматизация.

### `/pkg/wfexec`

.Ключевые моменты пакета `automation`:
- **Граф** инкапсулирует все шаги, определённые для конкретного рабочего процесса.
Графу необходимо пройти по узлам и выполнить их по порядку.
- **Шаг** — это узел графа, который выполняет требуемую операцию.
- **Сессия выполнения** инкапсулирует некоторую внутреннюю логику выполнения, отдельную от сессии автоматизации.

## Настройка

Настройка сервиса автоматизации инициализирует все суб-сервисы, заполняет реестр автоматизации и подготавливает механизм для выполнения рабочих процессов и получения результатов.

.Сервис автоматизации...
1. инициализирует все суб-сервисы, а также реестр автоматизации,
1. регистрирует все известные рабочие процессы и триггеры на шине событий,
1. инициализирует наблюдатель сессий, который будет обрабатывать запросы на выполнение.

Когда мы регистрируем рабочий процесс на шине событий, его триггеры преобразуются в набор интерфейсов `eventbus.ConstraintMatcher`; сам рабочий процесс преобразуется в `wfexec.Graph` логикой в `automation/service/workflow_converter.go`.
Первоначальная проверка рабочего процесса (структура, связи) выполняется при преобразовании его в `wfexec.Graph`.

!!! caution
    `wfexec.Step`, соответствующий `types.WorkflowStep`, может быть реализован за пределами пакета `wfexec`.


Основная обязанность наблюдателя сессий — инициализировать структуры `wfexec.Session` на корневом `context.Context`, когда они передаются в канал `spawnQueue`.

!!! caution
    Рабочие процессы выполняются на корневом `context.Context`, чтобы избежать случайного завершения контекста запрашивающим источником (например, HTTP-запросом, который вызвал выполнение).


## Выполнение

Выполнение рабочего процесса вызывается либо через шину событий, либо напрямую сервисом.

.Событие шины событий...
1. сопоставляет все обработчики, соответствующие предоставленному событию,
1. вызывает функцию-обработчик рабочего процесса (`automation/service/workflow.go@makeWorkflowHandler`) для подготовки контекста выполнения,
1. создаёт и запускает сессию автоматизации (`automation/service/session.go@.Start`).

Сервис сессий автоматизации создаёт структуру `automation.Session`, которая предоставляет основной контекст выполнения, и оборачивает `wfexec.Session`, который предоставляет контекст, специфичный для выполнения.

Создание `wfexec.Session` запускает `worker` (`pkg/wfexec/session.go@worker`), который выполняет шаги, передаваемые через канал `qState`.

!!! caution
    Каждый `wfexec.Session` запускает своего `worker` в горутине.


Когда выполняется `automation.Session`, он выполняет лежащий в основе `wfexec.Session`.
Когда шаг выполняется (`pkg/wfexec/session.go@.exec`), результат используется для определения следующего шага для выполнения.

## Обработчики и типы

Каждый сервис может определить модуль `automation`, который определяет типы данных и функции-обработчики для этого сервиса.

**Обработчики** определяются в файлах `automation/***handler.yaml` (например `automation/log*handler.yaml`) и генерируются в файлы `automation/**.gen.go` (например `automation/automation/log_handler.gen.go`).
Шаг-функция выполняет эти обработчики.

!!! caution
    Сгенерированные файлы реализуют шаблонный код для обработчика.
    Основная логика должна быть реализована отдельно (например, `automation/automation/log_handler.go`).


**Типы** определяются в файлах `automation/expr*types.yaml` (например `automation/automation/expr*types.yaml`) и генерируются в файлы `automation/expr*types.gen.go` (например `automation/automation/expr*types.gen.go`).
Эти типы реализуют интерфейс `expr.TypedValue` и могут использоваться в выражениях.

!!! caution
    Сгенерированные файлы реализуют шаблонный код для типа.
    Если тип требует дополнительной сложности (например, селекторы gval), вы должны реализовать их вручную.


## Бесконечное выполнение

Шаг рабочего процесса может вызывать сам себя или другой рабочий процесс.
Это может привести к бесконечному выполнению рабочего процесса.

Чтобы противостоять этому, мы реализовали проверку во время выполнения с использованием `callStack`, передаваемого через `context.Context`.

.Поток:
1. когда рабочий процесс запускается, извлеките текущий `callStack` из контекста,
1. если размер `callStack` превышает настроенный лимит, завершите с ошибкой,
1. если размер `callStack` не превышает настроенный лимит, передайте `callStack` в `wfexec.Session`.
