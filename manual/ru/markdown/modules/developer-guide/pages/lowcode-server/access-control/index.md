# Контроль доступа

LowCoooode определяет механизм контроля доступа на основе [RBAC](https://en.wikipedia.org/wiki/Role-based*access*control).
RBAC использует [glossary-role,**роли**](#glossary-role,**роли**) данного [glossary-user,**пользователя**](#glossary-user,**пользователя**) для определения наличия доступа к данному [glossary-resource,**ресурсу**](#glossary-resource,**ресурсу**).

Механизм контроля доступа должен вызываться всякий раз, когда субъект пытается получить доступ к защищённому ресурсу.
Единственным исключением являются ресурсы, к которым обращается только сама система, такие как настройки, параметры конфигурации и прочие системные метаданные.

!!! note
    *DevNote* некоторые диаграммы, описывающие различные потоки


## Обзор структуры

### `pkg/rbac`

!!! important
    Правила RBAC загружаются в память и доступны оттуда.
    Слой хранилища задействуется только при загрузке, перезагрузке или обновлении правил RBAC.


`pkg/rbac` содержит основную логику, на которую в дальнейшем ссылаются другие компоненты и их сервисы.

.Важные части пакета:
- `rbac.service` (структура): инкапсулирует управление правилами и логику проверки контроля доступа.
Инициализируется с помощью `rbac.NewService(...)`.
Синглтон можно инициализировать с помощью `rbac.SetGlobal(...)` и получить к нему доступ через `rbac.Global()`.
- `rbac.Resource` (интерфейс): общий интерфейс для более структурированной обработки ресурсов
- `rbac.Session` (интерфейс): интерфейс защищённой сессии для конкретных комбинаций пользователь-роли.
Предопределённые структуры можно инициализировать с помощью `rbac.ContextToSession(...)` или `rbac.NewSession(...)`.

### `<component>/service`

Каждый сервис компонента определяет структуру `accessControl`, которая генерируется из файлов `def/\*.yaml`.
Подробнее см. подразделы раздела [extending](#extending).

Структура `accessControl` определяет все ресурсы и операции, относящиеся к данному компоненту, и выступает в качестве прокси к внутреннему `pkg/rbac.Service`.
Структура `accessControl` также выполняет журналирование предоставления прав, проверку и контроль доступа.

## Расширение

### Добавление нового ресурса

Чтобы добавить совершенно новый ресурс, определите новый файл в каталоге `/def`.

Файл должен соответствовать шаблону: `\{component\}(.\{resource\}).yaml`.
Например: `system.user.yaml`.

Если вы определяете правила уровня компонента, опустите часть `(.\{resource\})`.
Например: `system.yaml`.

.Шаблон содержимого
```yaml
```
rbac:
  operations:
    {operation}:
      description: {optional notes here}

!!! note
    Здесь используется новый WIP-кодогенератор v3; запустите `go run pkg/codegen-v3/*.go def`


### Добавление новых правил к существующим ресурсам

Чтобы добавить новое правило к существующему ресурсу, откройте файл в каталоге `/def`.

Файл должен соответствовать шаблону: `\{component\}(.\{resource\}).yaml`.
Например: `system.user.yaml`.

Если вы определяете правила уровня компонента, опустите часть `(.\{resource\})`.
Например: `system.yaml`.

Если файл ещё не существует, создайте его.

Добавьте запись в раздел `rbac.operations`

.Шаблон содержимого
```yaml
```
rbac:
  operations:
    {operation}:
      description: {optional notes here}

## Типы ролей

!!! important
    Список ролей типа bypass, authenticated и anonymous нельзя изменять во время выполнения.
    Эти роли нельзя модифицировать или переименовывать.
    
    Если роль назначена как bypass, она *не может* быть представлена как другой тип роли (например, authenticated или anonymous).
    Если это условие не выполняется, LowCoooode откажется запускаться.


### Bypass

Роли bypass предоставляют своим участникам неограниченный доступ к LowCoooode без какой-либо проверки разрешений.

Список ролей bypass определяется в переменной `.env` `RBAC*BYPASS*ROLES` и не может быть изменён во время выполнения.
Роль по умолчанию — `super-admin`.

### Common

Common роли — это любые дополнительные роли, определяемые в панели администрирования, например администратор CRM и разработчик приложений.

### Contextual

Contextual роли определяют набор **выражений**, которые определяют, когда роль назначается пользователю на основе контекста операции.

Каждая роль может определять выражение для каждого типа ресурса.
Каждая роль может использовать тип ресурса только один раз.

Пример варианта использования позволил бы нам назначать роли владельцам ресурсов, что дало бы им разрешения, которых у них не должно быть в отношении других ресурсов.

### Authenticated

Authenticated роли являются **неявными**, то есть пользователи не могут быть явно назначены участниками таких ролей.

Список ролей authenticated определяется в переменной `.env` `RBAC*AUTHENTICATED*ROLES` и не может быть изменён во время выполнения.
Роль по умолчанию — `authenticated`.

### Anonymous

Anonymous роли являются **неявными**, то есть пользователи не могут быть явно назначены участниками таких ролей.

Список ролей anonymous определяется в переменной `.env` `RBAC*ANONYMOUS*ROLES` и не может быть изменён во время выполнения.
Роль по умолчанию — `anonymous`.

## Важность ролей

Важность ролей определяет порядок, в котором оцениваются предоставленные роли и соответствующие им правила.

.Важность ролей для аутентифицированных пользователей:
1. bypass роли
1. context роли
1. common роли
1. authenticated роли

.Важность ролей для анонимных пользователей:
1. anonymous роли

## Идентификаторы ресурсов

.Структура идентификатора ресурса соответствует следующему шаблону:
```
```
{rbac-ns}:: <1>
  {component}: <2>
  {service} <3>
  {path} <4>
<1> Пространство имён RBAC позволяет нам группировать правила RBAC по области, что позволит нам поддерживать пользовательские правила в будущем.
Пространство имён должно соответствовать регулярному выражению `[a-z]*`
<2> Компонент должен соответствовать регулярному выражению `[a-z]*`
<3> Сервис должен соответствовать регулярному выражению `[a-zA-Z]+`
<4> Путь должен соответствовать шаблону `(/[\**,a-z,A-Z,0-9]\**)+`

При определении идентификаторов ресурсов n-й элемент пути должен быть более или равно специфичным, чем (n+1)-й элемент пути.
Следующий пример недействителен, поскольку первый элемент менее специфичен (подстановочный знак `\**`), чем второй: `lowcode::compose:record/\**/21/2`.

<a id="resource-specificity"></a>
### Специфичность ресурса

Специфичность ресурса определяет порядок, в котором оцениваются правила для соответствующих ресурсов.
Специфичность ресурса определяется на основе «насколько конкретно данное правило относится к данному ресурсу».

Например, правило, разрешающее пользователям создавать записи в модуле учётной записи в пространстве имён CRM, более специфично, чем просто правило по пространству имён CRM.

Под капотом это вычисляется на основе количества подстановочных символов (`*`) в определении ресурса.
Если ресурс не содержит подстановочных символов, уровень равен 0.
Если ресурс содержит n подстановочных символов, уровень равен n-1 (с нулевой базой).

### Примеры идентификаторов ресурсов

Разрешения компонента Compose::
  `lowcode::compose/`

Разрешения для любого пространства имён (уровень=1)::
  `lowcode::compose:namespace:/*`

Разрешения для конкретного пространства имён (уровень=0)::
  `lowcode::compose:namespace:/42`

Разрешения для всех записей в конкретном пространстве имён (уровень=2)::
  `lowcode::compose:record/42/\*/*`

Разрешения для всех записей в любом пространстве имён или любом модуле (уровень=3)::
  `lowcode::compose:record/\**/*/**`

Разрешения для конкретной записи (уровень=0)::
  `lowcode::compose:record/42/21/2`

Разрешения для значений записей в полях конкретного модуля (уровень=0)::
  `lowcode::compose:moduleField/42/21/12`

## Поток оценки доступа

Доступ оценивается на основе контекста безопасности (а именно [role-importance,**важности ролей**](#role-importance,**важности ролей**) и [resource-specificity,**специфичности ресурса**](#resource-specificity,**специфичности ресурса**)) и операции, которую пытаются выполнить.

.Поток оценки доступа:
1. Если какое-либо правило явно определяет **deny**, оценка даёт результат **deny**.
1. Если хотя бы одно правило явно определяет **allow**, оценка даёт результат **allow**.
1. Если на текущем уровне нет явного allow или deny, оценка переходит к следующему набору правил на основе важности ролей.
1. Если оценка не может найти явного allow или deny, оценка даёт результат **deny**.

******
.Исходный поток оценки RBAC:
[%collapsible.example]
1. может ли данная комбинация ролей выполнить операцию над этим конкретным ресурсом
1. может ли данная комбинация ролей выполнить операцию над любым ресурсом данного типа (подстановочный знак)
1. может ли кто-либо/каждый выполнить операцию над этим конкретным ресурсом
1. может ли кто-либо/каждый выполнить операцию над любым ресурсом данного типа (подстановочный знак)
******

## Глоссарий

|===
| [#glossary-user]#[glossary-user,Пользователь](#glossary-user,Пользователь)#

Пользователь — это субъект, который обращается к LowCoooode.
Пользователь может быть участником ролей безопасности и не может получать разрешения напрямую без назначенной роли.

| [#glossary-role]#[glossary-role,Роль](#glossary-role,Роль)#
|
Роль представляет собой набор пользователей и набор разрешений над ресурсами.

Реализация RBAC в LowCoooode определяет плоскую структуру, которая устраняет иерархию ролей (две роли не могут явно указывать связь родитель/ребёнок).

|

| [#glossary-resource]#[glossary-resource,Ресурс](#glossary-resource,Ресурс)#
|
Структурированная часть информации, хранящейся в LowCoooode, доступ к которой мы можем контролировать или не контролировать.
Каждый ресурс принадлежит компоненту и имеет уникальный тип.

| [#glossary-resource-type]#[glossary-resource-type,Тип ресурса](#glossary-resource-type,Тип ресурса)#
|

| [#glossary-operation]#[glossary-operation,Операция](#glossary-operation,Операция)#
|
Определяет, к какой операции предоставляет доступ данное правило RBAC.

|
Правило RBAC объединяет **операцию**, **роль**, **доступ** и **ресурс**.
Оно определяет, что кто-то может (или не может) делать с одним или несколькими ресурсами внутри LowCoooode.

| [#glossary-security-session]#[glossary-security-session,Сессия безопасности](#glossary-security-session,Сессия безопасности)#
|
Сессия безопасности создаётся, когда пользователь запрашивает доступ к LowCoooode.
