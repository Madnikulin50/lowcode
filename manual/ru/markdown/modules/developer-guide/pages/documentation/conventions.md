# Соглашения

При написании текстов используйте следующие соглашения как ориентир, особенно когда вы хотите добавить к своим документам дополнительное форматирование.

Приведённый ниже список собран из [AsciiDoc](https://asciidoctor.org/docs/asciidoc-syntax-quick-reference/), сокращён и адаптирован под наши нужды.

Пожалуйста, приложите все усилия, чтобы **следовать соглашениям**, перечисленным ниже, при внесении вклада в документацию.

Мы довольно строги в отношении **1 предложения на строку**, чтобы иметь более качественную историю версий документа в производстве.

## Композиция, оформление, макет

При составлении любого текста важно уделять внимание его оформлению и макету, особенно когда речь идёт о документах, **просматриваемых с электронных устройств**.

Крайне важно создавать документ, который **легко понять** и **стабилен** как с точки зрения содержания, так и с визуальной точки зрения.
Последовательность имеет решающее значение.

Хорошо бы:

.Визуальная группировка
- Убедитесь, что вы группируете компоненты, которые подходят друг к другу, т.е. обсуждения одной и той же концепции, концепция и пример, подпункты и советы...

!!! note
    Если что-то не относится к разделу, перенесите это в другое место.
    Лучше добавить раздел, чем поступиться связностью и плавностью документа.


.Привлечение внимания к ключевым моментам
- Используйте **жирный шрифт**, **курсив**, **ссылки**, **встроенные блоки кода** и другие средства форматирования, чтобы выделить любые ключевые моменты.
- **Не переусердствуйте**, так как чрезмерное выделение приводит к снижению внимания к выделенным разделам.

## Списки

Вы можете использовать списки, чтобы придать документу **дополнительную структуру**, **обозначить** ключевые моменты, отобразить **последовательность** и т.д.
Старайтесь делать списки **короткими**, так как они могут затруднить чтение документа.

.Пунктуация:
- Если элемент списка является **полным предложением**, начинайте с **заглавной буквы** и заканчивайте **точкой**.
- Если элемент списка **не** является **полным предложением**, начинайте со **строчной буквы** и (по желанию) заканчивайте **запятой**.
Если вы решите использовать запятые, начинайте первый элемент с заглавной буквы и заканчивайте последний точкой. 
- Если весь список представляет собой одно предложение, разбитое на пункты-клаузы, убедитесь, что первый элемент списка начинается с заглавной буквы, пункт заканчивается запятой, следующий пункт продолжается со строчной буквы, заканчивается запятой и так далее.
Завершите список точкой.
- Не смешивайте типы предложений при составлении списка.

.Пример полного предложения; план наших документов:
- **Руководство пользователя приложения** рассказывает о вещах, актуальных для конечных пользователей.
- **Руководство разработчика low-code платформы** рассказывает о создании новых вещей на основе LowCoooode.
- **Руководство разработчика платформы** помогает основным разработчикам отслеживать, как обслуживать различные функции.

### Упорядоченные списки

Элементы **упорядоченного списка** должны **начинаться с точки** (`. ...содержимое здесь...`) вместо фактического номера (он присваивается во время компиляции).
Пожалуйста, посмотрите пример ниже.

```adoc
```
.Здесь мы можем увидеть:
1. элемент списка 1,
1. элемент списка 2.

При отступе элемента строки следует использовать несколько точек.
Пожалуйста, посмотрите пример ниже.

1. пункт (становится 1.)
.. подпункт (становится a.)
... подпункт подпункта (становится i.)

### Неупорядоченные списки

Элементы **неупорядоченного списка** должны **начинаться со звёздочки** (`* ...содержимое здесь...`).
Пожалуйста, посмотрите пример ниже.

```adoc
```
.Здесь мы можем увидеть:
- элемент списка 1,
- элемент списка 2.

При отступе элемента строки следует использовать несколько звёздочек (символ `*`).

!!! tip
    Если элементы вашего списка длинные, попробуйте переструктурировать раздел или используйте многострочные блоки описания.


### Многострочные блоки описания

Используйте блоки описания, когда ваши **списки** начинают **становиться длинными**.
Они сначала представляют **ключевой момент** блока, за которым следует более **подробное описание**, смещённое вправо.

```adoc
```
[Ключевой момент здесь]::
    [Описание здесь].

В качестве примера:
```adoc
```
## Структура документации LowCoooode

Руководство по DevOps::
    Руководство по DevOps охватывает все связанные с DevOps аспекты, такие как развёртывание и обслуживание.
    ...

Руководство пользователя приложения::
    Руководство пользователя приложения служит справочником для конечных пользователей, которым нужна помощь в использовании пользовательского интерфейса LowCoooode.
    ...

Руководство разработчика low-code платформы::
    Руководство разработчика low-code платформы служит справочником для интеграторов — людей, которые хотят создавать вещи с помощью LowCoooode.
    ...


!!! important
    Старайтесь не злоупотреблять этим.
    Если ваши описания *становятся длинными*, лучше переструктурировать и разделить текст на несколько подразделов.

## Примечания (Admonitions)

Используйте **синтаксис блока примечаний**, когда вы хотите создать примечания; где вы хотите **привлечь дополнительное внимание**.

.Вы можете использовать следующие:
- NOTE
- TIP
- IMPORTANT
- WARNING
- CAUTION

Эти типы в основном говорят сами за себя.
Не злоупотребляйте.

## Диаграммы

**Используйте фреймворк [PlantUML](https://plantuml.com/)** для любых диаграмм (если только для этого нет явной причины).
Это позволяет нам **поддерживать единообразие**, **сохранять историю версий** и **легко поддерживать**.

!!! tip
    Переносите *более крупные диаграммы* в *отдельные файлы*, чтобы избежать захламления и нечитаемого исходного кода.


Дайте хорошую подпись, обобщающую **всю** диаграмму. 
Для подписи диаграммы не следует использовать более одной строки.

```
[plantuml,имя-диаграммы-здесь,svg,role=имя-диаграммы]
@startuml

' Определение диаграммы идёт здесь

@enduml
```

!!! tip
    Более крупные диаграммы может быть труднее понять.
    Приложите все усилия, чтобы *сгруппировать элементы вместе*, и используйте хороший *комментарий*, чтобы указать на это.


Подписи к диаграммам::
    Подпись **должна быть достаточной**, чтобы читатель получил представление о том, **что происходит** на диаграмме.
    Убедитесь, что подпись даёт читателю достаточно понимания, чтобы иметь представление о том, **что он может ожидать узнать** **из диаграммы**.

Комментарии::
    Комментарий PlantUML начинается с `'` (одна строка) или заключён между `/'` и `'/`.
    Пожалуйста, используйте следующее обозначение ради единообразия;

```adoc
```
' ---------------
' Определяйте комментарии вот так.
' Несколько строк допустимы.
' ---------------

Структура диаграммы::
    Вы можете свободно использовать любую диаграмму и любой компонент, определённый диаграммой.
    **Избегайте визуальной настройки** с помощью **Skinparam**.

## Ссылки

Используйте ссылки, чтобы **связывать разные части** информации.
Мы используем **два различных типа** ссылок:

Перекрёстные ссылки на страницы::
    **Перекрёстные ссылки на страницы** позволяют нам связывать **между разными документациями**, или даже разными версиями.
    Используйте макрос `xref` ([Документация Antora](https://docs.antora.org/antora/2.2/asciidoc/page-to-page-xref/)):

```adoc
```
[метка-здесь](руководство-здесь/путь-до-источника.md)

[Рабочие процессы](integrator-guide/workflows/index.md)

!!! tip
    Вы также можете использовать *якоря* в своих `xref`.


Ссылки на той же странице::
    **Ссылки на той же странице** позволяют нам ссылаться в разделе одной и той же документации.
    Используйте простой синтаксис ссылки на идентификатор страницы ([Документация Antora](https://docs.antora.org/antora/2.2/asciidoc/in-page-xref/)):

```adoc
```
<a id="id-идёт-здесь"></a>

[id-идёт-здесь](#id-идёт-здесь)

[id-идёт-здесь,настраиваемая-метка-здесь](#id-идёт-здесь,настраиваемая-метка-здесь)

### Важные замечания

Ссылки на той же странице просты::
    Ссылки на той же странице могут **ссылаться только** на то, что **находится на текущей странице**.
    Если вы попытаетесь сослаться на что-то, чего **нет на экране**, ссылка **не будет работать**.
    Используйте **перекрёстные ссылки на страницы**.

Делайте идентификаторы секций простыми::
    Идентификаторы секций значимы **только для данной страницы**.
    Они не должны быть **уникальными** во всей документации, только **для текущей страницы**.
    В качестве примера; `[#extension-deployment]`

Не переусердствуйте::
    Если что-то **требуется для понимания** данного раздела, добавьте **краткое резюме** и укажите ссылку на полный документ после этого.
