# Цикл релизов

## Терминология

[cols="3s,9a"]
|===
| [#rc-terminology-major*version]#[rc-terminology-major*version,Основная версия](#rc-terminology-major_version,Основная версия)#
|
Основные версии (называемые релизом) выходят два раза в год: в последние недели марта и сентября (ранее ежеквартально с дополнительным релизом в июне и декабре).
Версии имеют префикс из полного года и номера квартала (`YYYY.Q`; стандарт [CalVer](https://calver.org/)); например, `2020.12` обозначает последний релиз 2020 года.

| [#rc-terminology-version*branch]#[rc-terminology-version*branch,Ветка версии](#rc-terminology-version_branch,Ветка версии)#
|
Ветка версии содержит код, включённый в этот релиз; например, ветка `2021.3.x` содержит весь код, выпущенный в версии `2021.3`.
Ветка версии имеет суффикс `.x` и создаётся, как только мы начинаем работать над этой версией.

| [#rc-terminology-feature*branch]#[rc-terminology-feature*branch,Функциональная ветка](#rc-terminology-feature_branch,Функциональная ветка)#
|
Функциональная ветка содержит весь код конкретной версии; например, ветка `2021.3.x-feature-workflow` содержит весь код начальной реализации рабочих процессов.
Функциональная ветка имеет суффикс `-feature-<описание>` и создаётся, как только мы начинаем работать над этой функцией.
Функциональные ветки недолговечны и удаляются, когда функция сливается в [rc-terminology-version*branch,ветку версии](#rc-terminology-version*branch,ветку версии).

| [#rc-terminology-release]#[rc-terminology-release,Релиз](#rc-terminology-release,Релиз)#
|
Релиз — это git-тег на последнем стабильном коммите ветки версии.
Git-тег следует шаблону `YYYY.Q.R`, где `R` представляет собой инкрементальный номер (с нуля) этого релиза.
Например, `2021.3.0` обозначает первый релиз `2021.3`.

| [#rc-terminology-patch*release]#[rc-terminology-patch*release,Патч-релиз](#rc-terminology-patch_release,Патч-релиз)#
|
Патч-релиз — это git-тег на последнем стабильном коммите уже выпущенной ветки версии.
Git-тег следует шаблону `YYYY.Q.R`, где `R` представляет собой инкрементальный номер (с единицы) этого патч-релиза.
Например, `2021.3.1` обозначает первый патч-релиз `2021.3`.

!!! note
    Патч-релиз обычно называют «релизом».


| [#rc-terminology-dev*release]#[rc-terminology-dev*release,Релиз для разработки (dev)](#rc-terminology-dev_release,Релиз для разработки (dev))#
|
Релиз для разработки — это ***нестабильный*** релиз функций, находящихся в разработке и запланированных для предстоящего релиза.
Git-тег следует шаблону `YYYY.Q.R-dev.D`, где `D` представляет собой инкрементальный номер (с единицы) этого релиза.
Например, `2021.3.0-dev.3` обозначает третий dev-релиз `2021.3.0`.

| [#rc-terminology-release*candidate]#[rc-terminology-release*candidate,Кандидат на релиз (RC)](#rc-terminology-release_candidate,Кандидат на релиз (RC))#
|
Кандидат на релиз — это git-тег на последнем коммите ветки версии.
Кандидат на релиз означает, что стабильность ветки приближается к готовности для основного релиза. 
Git-тег следует шаблону `YYYY.Q.R-rc.C`, где `C` представляет собой инкрементальный номер (с нуля) этого релиза.
Например, `2021.3.0-rc.3` обозначает четвёртого кандидата на релиз `2021.3.0`.

| [#rc-terminology-version]#[rc-terminology-version,Версия](#rc-terminology-version,Версия)#
|
Термин «версия» может относиться к одному из терминов [release,релиз](#release,релиз), [feature,функция](#feature,функция), [version*branch,ветка версии](#version*branch,ветка версии), [patch*release,патч-релиз](#patch*release,патч-релиз) или [release*candidate,кандидат на релиз](#release*candidate,кандидат на релиз)

|===

## Git(Hub)

Вся разработка LowCoooode обеспечивается Git и GitHub (GH).
Чтобы сделать разработку последовательной и лёгкой для отслеживания, мы ввели несколько правил, которым должны следовать участники.

### Очистка и rebase функциональных веток

Перед тем как функциональная ветка будет слита в ветку релиза, её нужно перебазировать (rebase) на ветку релиза, чтобы уменьшить размер диффа.
Мы рекомендуем регулярно выполнять rebase, чтобы уменьшить потенциальные конфликты слияния.

Кроме того, используйте интерактивный rebase, чтобы перестроить историю git, которую вносит ваша функциональная ветка, сделав её чище и короче.
История должна рассказывать историю.
Иногда проще воссоздать всю историю коммитов, когда вы закончили первую версию функции.

### Слияние ветки

Если исходная ветка небольшая (горсть коммитов), используйте слияние с ускорением (fast-forward merge — слияние без коммита слияния).
Если исходная ветка вносит значительные изменения (она вводит новые функции), используйте слияние без ускорения (не fast-forward merge — слияние с коммитом слияния).

!!! important
    Удалите ветку после её слияния.
    Только основным участникам иногда разрешается забывать это делать.


### Переименование отложенных функциональных веток

Если функция откладывается до следующего релиза, переименуйте ветку в соответствии с веткой того релиза.
Например, если `2020.12.x-feature-foo` откладывается до `2021.3.x`, функциональную ветку нужно переименовать в `2021.3.x-feature-foo`.

### Избегайте коммитов напрямую в ветку версии

Незначительные изменения (такие как хотфикс) могут пропустить весь процесс pull request'а.
Более крупные изменения всегда должны проходить через процесс pull request'а.

### Бэкпортирование

Исправления ошибок или улучшения, которые также применимы к уже выпущенным версиям, переносятся (cherry-pick) коммитами в эти ветки версий.
При бэкпортировании сводите изменение к одному коммиту с ясным и описательным сообщением коммита.

### Ветка версии в разработке

Каждый раз, когда происходит релиз и создаётся следующий набор веток версий, ветка GitHub по умолчанию перемещается на вновь созданную ветку версии.
Это облегчает вклад новых участников, а также позволяет нам демонстрировать новейшую и лучшую версию.

Ожидается, что ветка версии в разработке будет перебазирована на текущую ветку релиза, чтобы отложить расхождение веток из-за патчей после релиза.
Rebase обычно прекращается, когда начинают применяться новые функции.

## FAQ

### Почему не Git flow?

Git flow — отличная идея, которая хорошо работает на бумаге.
Он отказывается от rebase и делает историю проекта (git) полностью нечитаемой после пары слияний.

### Где ветка `main`?

Поддержание ветки `main` затруднило бы понимание того, с какой версией мы работаем.
Использование веток версий делает вещи более прямолинейными.
